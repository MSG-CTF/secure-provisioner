생성 응답을 잃은 경우 스케줄러는 원래 생성 본문을 reconcile_create에 보냅니다

- 이미 접수됐다면 기존 작업 ID와 상태를 돌려주고 작업을 계속 추적합니다
- 미접수라면 같은 요청 ID를 실패로 종료하고 정리 완료를 표시합니다
- 종료 기록과 생성 접수는 DB의 같은 요청 ID 고유 제약으로 경쟁하므로 한쪽만 먼저 저장됩니다
- 종료 기록이 먼저 저장되면 뒤늦은 생성과 재전송은 같은 실패 기록을 받으며 실행되지 않습니다
- 기존 작업이 먼저 저장되면 생성 완료 또는 롤백을 기다린 뒤 삭제합니다

스케줄러는 정리 완료 증명이나 실제 삭제 완료를 확인한 뒤 예약을 반납합니다
접수 확인 자체가 실패하면 정리 대기와 예약을 유지하고 다시 확인합니다

배포는 런타임을 먼저 반영하고 스케줄러를 반영합니다
구버전 런타임이 새 경로에 404를 반환하면 스케줄러는 기존 상태 조회를 이어가며 정리 완료로 판단하지 않습니다
운영 환경에서는 PostgreSQL 저장 모드를 사용해야 재시작 후에도 종료 기록이 남습니다
생성 요청 ID 기록은 지연된 요청이 다시 도착할 수 있는 동안 삭제하면 안 됩니다

생성 중 런타임 프로세스가 종료된 경우

- PostgreSQL worker는 작업별 session advisory lock을 실행 시작부터 결과 저장까지 유지합니다
- DB lease가 만료돼도 실행 잠금이 남아 있으면 다른 worker는 해당 작업을 건너뜁니다
- 프로세스가 종료되면 PostgreSQL이 잠금을 해제하고, 재시작한 worker는 기존 lease 만료 후 같은 작업 ID를 회수합니다
- 첫 시도부터 실행 잠금을 사용했다는 기록과 현재 잠금이 모두 있어야 회수한 작업의 정리 완료 증명을 허용합니다
- Kubernetes adapter가 소유 Namespace의 UID를 확인하고 실제 삭제 완료를 확인해야 cleanup_completed를 반환합니다
- 실행 잠금만 획득했거나 Namespace 조회에 실패한 경우에는 정리 완료 증명이 생기지 않습니다
- 잠금용 연결이 끊기면 실행 context를 취소하고, 해당 연결을 풀에 재사용하지 않습니다
- 잠금 연결 풀은 30개로 제한하며 API 조회와 lease 갱신에 사용하는 풀과 분리합니다

실제 Namespace가 남은 생성 작업을 회수하면 같은 자원을 다시 만들지 않고 정리 후 실패로 종료할 수 있습니다
이때 스케줄러는 기존 cleanup_completed 계약으로 인스턴스를 종료하고 예약을 반납하며, 사용자는 새 생성을 요청할 수 있습니다
같은 인스턴스가 RUNNING으로 복구되는 것만을 재시작 성공 조건으로 삼지 않습니다

구버전 worker와 혼합 실행하지 말고 기존 배포 handoff로 실행 중인 작업을 비운 뒤 새 worker를 시작합니다
이미 구버전에서 실행된 작업은 실행 잠금 이력이 없어 회수 후에도 정리 완료로 자동 승격하지 않습니다
기존 CLEANUP_PENDING 행은 별도로 자원 부재와 실행 중인 구버전 worker 부재를 확인한 뒤 운영자 정리 절차를 적용합니다
