생성 응답을 잃은 경우 스케줄러는 원래 생성 본문을 reconcile_create에 보냅니다

- 이미 접수됐다면 기존 작업 ID와 상태를 돌려주고 작업을 계속 추적합니다
- 미접수라면 같은 요청 ID를 실패로 종료하고 정리 완료를 표시합니다
- 종료 기록과 생성 접수는 DB의 같은 요청 ID 고유 제약으로 경쟁하므로 한쪽만 먼저 저장됩니다
- 종료 기록이 먼저 저장되면 뒤늦은 생성과 재전송은 같은 실패 기록을 받으며 실행되지 않습니다
- 기존 작업이 먼저 저장되면 생성 완료 또는 롤백을 기다린 뒤 삭제합니다

스케줄러는 정리 완료 증명이나 실제 삭제 완료를 확인한 뒤 예약을 반납합니다
접수 확인 자체가 실패하면 정리 대기와 예약을 유지하고 다시 확인합니다

배포는 런타임을 먼저 반영하고 스케줄러를 반영합니다
구버전 런타임이 새 경로에 404를 반환하면 스케줄러는 기존 상태 조회를 이어가며 정리 완료로 판단하지 않습니다
운영 환경에서는 PostgreSQL 저장 모드를 사용해야 재시작 후에도 종료 기록이 남습니다
생성 요청 ID 기록은 지연된 요청이 다시 도착할 수 있는 동안 삭제하면 안 됩니다
