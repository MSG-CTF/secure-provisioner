# WEB 생성 대기와 종료 처리

12명 동시 검증에서는 운영의 `PROVISIONER_WORKERS=8` 때문에 뒤의 네 요청이
작업자 자리를 기다렸습니다 Cashout의 실행은 약 6초였지만, 일부 요청에
11초의 큐 대기가 더해졌습니다 이 환경의 다음 적용 후보는 12개입니다

```dotenv
PROVISIONER_WORKERS=12
```

프로그램의 기본값 10은 유지합니다 이미 설정된 운영의 8은 예제 파일을
수정해도 바뀌지 않으므로, 운영 환경 파일과 GitHub `control-production`의
`DEPLOY_ENV`를 함께 갱신해야 합니다 적용 전에는 작업을 비우고, API bridge를
거쳐 검증한 바이너리와 설정을 함께 반영합니다

이 설정은 문제 컨테이너의 CPU나 실행 노드를 늘리지 않습니다 브로커의 기동
CPU 예약과 기본 CPU 복귀 확인, 삭제 확인 뒤 반납 순서를 유지합니다
PostgreSQL 실행 잠금 연결 풀과 일반 조회·lease 갱신 풀도 기존처럼 분리합니다
Gateway의 동시 반영 수와 polling 주기는 이번 변경에서 유지합니다

Grade Tampering은 승인한 정확한 이미지 digest에 `python_sigint_child`를
설정합니다 셸 아래의 Python 주 프로세스 하나에만 종료 신호를 전달하며,
대상 확인이 실패하면 기존 유예시간을 따릅니다 CPU 기동·원복 과정에서도
이 hook을 보존합니다 문제 소스·이미지·명령·환경변수는 바꾸지 않습니다

반영 시에는 세 문제에서 네 팀씩 생성·접속·동시 삭제를 확인하고, 다음을
함께 대조합니다

- 실제 기동 CPU와 기본 CPU 적용값, 컨테이너 재시작 없음
- 요청별 큐 대기와 실행 시간, 전체 완료 시간
- namespace·접속 경로·바인딩의 실제 삭제
- 한 번의 생성과 삭제, 삭제 확인 이후 예약 반납
- 제어 서버 CPU·메모리와 PostgreSQL 연결 수

12개를 넘는 동시 요청이나 다른 문제 조합의 성능을 보장하는 설정은 아닙니다
원복은 새 요청을 멈추고 생성·삭제를 끝낸 다음 이전 설정과 바이너리로
진행합니다 기동 CPU 부스트의 기존 활성 상태는 유지합니다
