# 2026-09-09 로컬 K3s 검증 결과

관련 이슈: #11, #40. 검증 대상 정책은 Runtime PR #41의 `STANDARD@v2`다.

## 환경 및 한계

- Linux amd64, Go `go1.26.7`.
- 이번 검증을 위해 별도로 생성한 K3s `v1.36.4+k3s1`, containerd `2.3.4-k3s1.36`.
- K3s 기본 flannel 및 NetworkPolicy controller, `NODE_PORT` 공개 방식.
- `tests/fixtures/network-probe`의 제한된 BusyBox HTTP 서버를 사용했다.
- 이미지가 미리 적재된 단일 노드 실습 환경이다. GHCR pull, AWS/SSM 경로,
  운영 Registry/Scheduler 및 여러 노드 사이의 통신은 이 결과에 포함되지 않는다.
- PID, Admission, RuntimeClass 및 노드·metadata 경계는 별도로 검증해야 한다.

## 실제 NetworkPolicy 검증

[실행 방법과 판정 기준](../instance-network.md)에 따라 실제 Adapter로
인스턴스 3개와 Pod 6개를 만들었다. 같은 팀의 별도 인스턴스와 다른 팀의 인스턴스를
각각 포함했다. 테스트의 정상·차단 판정과 Namespace 정리가 모두 통과했다.

```text
--- PASS: TestK3sLiveInstanceNetwork (225.08s)
    --- PASS: TestK3sLiveInstanceNetwork/instance-0-internal-and-dns (8.18s)
    --- PASS: TestK3sLiveInstanceNetwork/instance-1-internal-and-dns (9.04s)
    --- PASS: TestK3sLiveInstanceNetwork/instance-2-internal-and-dns (8.23s)
    --- PASS: TestK3sLiveInstanceNetwork/same-team-other-instance (14.12s)
    --- PASS: TestK3sLiveInstanceNetwork/other-team (14.04s)
    --- PASS: TestK3sLiveInstanceNetwork/public-and-private-port-separation (0.09s)
PASS
ok  github.com/MSG-CTF/secure-provisioner/internal/k3s  225.091s
```

비공개 포트의 차단은 대상 내부의 정상 연결을 확인한 후 Service DNS 및 Pod IP로
각각 연속 3회 관찰했다. 차단 검사 중 연결 성공이나 `kubectl exec` 실패는 통과로
처리하지 않는다. 공개 포트는 외부 runner에서 실제 HTTP fixture 응답을 확인했다.

## DevSecOps 스크립트 → Runtime API → K3s

DevSecOps main `ac5a5a8298d12220a329f5a3be5aaa1efe51a62e`의
[`runtime_api_smoke_runner.py`](https://github.com/MSG-CTF/msgctf-devsecops/blob/ac5a5a8298d12220a329f5a3be5aaa1efe51a62e/scripts/runtime_api_smoke_runner.py)를
변경 없이 사용했다. Runtime binary는 `8ace152` 소스로 빌드하고 격리된 PostgreSQL
operation/binding store와 연결했다. 별도 생성한 임시 토큰 파일로 loopback API를 호출했다.

입력은 공개 web:8080, 비공개 api:9000의 두 컨테이너이며 `internal_connections`를
포함하지 않았다. revision 값은 이 실행용 fixture 식별자이며 Registry에 발행한
운영 revision이 아니다. 스크립트의 create/poll/delete/poll 결과는 다음과 같다.

```json
{
  "revision": "issue11-local-validation",
  "create_status": "SUCCEEDED",
  "delete_status": "SUCCEEDED",
  "recovered_after_timeout": false
}
```

관리 주소, 토큰, kubeconfig 및 내부 workload 식별자는 결과에서 제외했다.
AWS OIDC → S3 → SSM 전송과 Registry → Scheduler 호출 경로는 실행하지 않았다.

## 회귀 검사 및 남은 범위

- 전체 Go 테스트와 `go vet ./...` 통과. 일반 실행의 네트워크 테스트 skip은
  위의 별도 실환경 실행으로 검증했다.
- 전용 테스트에서 `K3S_NETWORK_REQUIRED=true`인데 입력이 없으면 실패하는 것을 확인했다.
- 실제 AWS 개발 대상 및 배포 Runtime revision 확인, caller의 삭제 필드/포트 변환,
  GHCR 인증 실패·cold pull, 운영 Registry/Scheduler 경로, #11의 나머지 격리는 남아 있다.

이 결과만으로 #11 또는 #40의 전체 연동 완료를 선언하지 않는다.
